# ArchIDE

**IDE для архитектурного графа, а не для кода.** Человек и агент работают с
архитектурой на понятном языке; код, диаграммы и документы — это **проекции**
единой модели, а не её источник.

## Зачем: следующий шаг после IDE

История программирования — это история **повышения уровня описания**. Каждый шаг
не отменял предыдущий, а снимал с человека ещё один слой рутины:

| Шаг | Что описывает человек | Кто делает рутинную работу |
|---|---|---|
| Машинный код | команды процессора | — |
| Ассемблер | мнемоники | ассемблер |
| Языки высокого уровня | алгоритмы и структуры данных | компилятор |
| IDE | код + навигация, рефакторинг, отладка | компилятор и инструменты |
| **ArchIDE** | **архитектуру системы** | **LLM как компилятор** |

Ассемблер избавил от машинных кодов, компилятор — от ассемблера, IDE — от
механической работы с текстом. Но **код человек всё ещё пишет руками**: систему он
проектирует на уровне архитектуры, а затем вручную переводит архитектуру в код —
самый дорогой и наименее обратимый шаг во всём цикле.

ArchIDE делает следующий шаг: **описание архитектуры становится исходником**, а
LLM — **компилятором** в код на языке высокого уровня. Архитектор формулирует
систему как граф (C4-каркас, аспекты, требования, интерфейсы, данные, состояния),
ArchIDE проверяет её непротиворечивость, а кодогенерирующий агент превращает её в
рабочий репозиторий — так же, как компилятор превращает программу в машинный код.

Отсюда требования, которые отличают ArchIDE от «чата с LLM»:

- **Исходник должен быть проверяемым.** Программу проверяет компилятор — архитектуру
  проверяют закрытая метамодель и валидатор (типы, якоря, кросс-аспектные связи,
  ограничения) с циклом доработки. Компилятор без проверки исходника — не компилятор.
- **Нужна отладка, а не «получилось / не получилось».** Для этого есть аспектные
  виды и линзы, срезы, уровни C4, **граф-дифф «цель ↔ результат»** и вердикт
  приёмки — инструменты отладки архитектуры, а не текста.
- **Нужна трассируемость.** Каждый элемент знает свой источник (код, документ,
  постановка), а сгенерированный код несёт подписанные метки — можно проверить,
  что реализовано именно спроектированное.
- **Нужен IDE-каркас.** Палитра команд, инспектор, навигация по уровням,
  подзакладки аспектов, дерево сущностей, визуальное редактирование, проекты,
  история и лента агента — то, чем архитектор работает каждый день.

Именно поэтому ArchIDE — **IDE**, а не генератор кода: она даёт архитектуре то, что
языки программирования получили за десятилетия — уровень описания, проверку,
отладку и инструменты.

> Архитектура — один типизированный граф. Код, диаграммы и документы — это
> представления этого графа. Сущность существует ровно один раз (одно «домашнее»
> место), все остальные места ссылаются на неё по стабильному ID.

## Идея

- **Динамическая устойчивость, а не «идеальная» онтология.** Мы **не пытаемся**
  построить абсолютно универсальную модель архитектуры под любые системы — это
  недостижимо. Вместо этого — **легко расширяемый граф** с простой логикой, а его
  непротиворечивость **проверяет и поддерживает агент**: цикл
  «наблюдение → расхождение → коррекция». Не идеальная базовая конструкция, но
  **динамически стабилизируемая** (см. `docs/Concept.md` §0.1).
- **Единый граф, а не куча документов.** В документной модели один смысл
  дублируется и расходится; в графовой — сущность существует один раз, остальное
  — ссылки.
- **Система субграфов.** Каркас, аспекты, агрегаты, проекции, срезы, версии и
  внешние свидетельства — всё это субграфы одного графа, связанные алгеброй
  `merge · common · minus · view · slice · agg · pin · changes` (см. `docs/Concept.md` §2).
- **Каркас (C4) + аспекты.** C4 — структурная идентичность (System→Container→
  Component→Module). Поведение, данные, интерфейсы, процессы, доступ, ИБ —
  ортогональные **аспекты**, натянутые на тот же каркас (см. `docs/Concept.md` §4).
- **Проекции, а не артефакты.** Диаграмма/спецификация вычисляется из модели —
  поэтому не может «разойтись» с ней.
- **Агенты работают по ограниченным срезам.** Из модели генерируется bounded-срез
  контекста для конкретной задачи; агент не видит всю систему.
- **Двухпроходная реконструкция.** Сначала по **исходному коду**, затем сравнение
  с **документацией**; расхождения (отклонения) показываются явно с указанием
  источника.
- **Строгость машинная, а не дисциплинарная.** Закрытая метамодель + валидатор +
  цикл доработки; неподделываемые метки трассируемости (см. `docs/Concept.md` §11).

## Текущее состояние (PoC)

Реализовано в `archide-poc/`:

- **Среда управления агентами:** реестр агентов (встроенный + **Kilo Code CLI**),
  запуск в **Docker-песочнице без bind-mount'ов** (sandbox-протокол по HTTP).
- **LLM-шлюз:** агенты ходят через шлюз со **своим токеном**; шлюз подставляет
  **настоящий** ключ инференса (в контейнер ключ не попадает).
- **Наблюдаемость:** живая лента активности (размышления/логи/статусы), принудительная
  остановка, асинхронные запуски.
- **Общий том** (аналог PVC) для всех агентов; бюджет контекста и **сжатие**
  (extract/truncate/drop).
- **Двухпроходная реконструкция** код → документация со **слиянием и отклонениями**;
  валидация на хосте и в агенте + цикл доработки (настраиваемое число попыток).
- **UI:** граф по одному уровню C4, хлебные крошки, zoom in/out, переключение
  источников (all/code/docs), self-contained SVG-рендер.

Не реализовано (см. дорожную карту): модель как хранилище-редактор, аспекты,
referential actions/транзакции/impact, подписанные метки, конформанс-слой.

## Быстрый старт

Зависимостей из PyPI нет — сервер и агент на стандартной библиотеке Python.

```bash
cd archide-poc
docker build -t archide-agent:latest agent/
docker build -t archide-kilo:latest agents/kilo/   # опционально: Kilo Code CLI
./run.sh            # -> http://127.0.0.1:8000
```

Без Docker/LLM: в UI выберите `mode = mock`, `runner = local` — весь конвейер
пройдёт без инференса.

Демо UI без сервера: откройте `archide-poc/frontend/index.html?demo=1`
(`&mode=code|docs`, `&focus=<node-id>`).

## Тесты (e2e)

Сквозные тесты сценариев (`docs/SCENARIOS.md`) в двух режимах — **API** и **браузер**
(headless Chrome, реальные действия пользователя), детерминированно (mock/local +
стаб-docker, без реального Docker и LLM):

```bash
bash tests/run_e2e.sh      # API + браузер; печатает E2E RESULT: PASS|FAIL
```

После каждой достаточно крупной доработки e2e обязателен (см. [`AGENTS.md`](AGENTS.md)).

## Дорожная карта (кратко)

`Ф0` PoC (среда агентов, частично) → `Ф1` продуктизация песочницы → `Ф2`
универсальная модель архитектуры → `Ф3` полная реконструкция из кода и
документации (с валидацией) → `Ф4` редактирование модели и автоматическая
непротиворечивость → `Ф5` генерация и валидация кода по модели.

Полностью: [`docs/ROADMAP.md`](docs/ROADMAP.md).
