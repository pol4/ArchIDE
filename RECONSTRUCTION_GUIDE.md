# ArchIDE — полная реконструкция реального проекта (все аспекты)

Практическая инструкция, снятая с **реального прогона**: репозиторий
[`pol4/MLScan`](https://github.com/pol4/MLScan) вместе с папкой архитектурной
документации [`Arch_v3`](https://github.com/pol4/MLScan/tree/main/Arch_v3)
(17 документов: обзор, требования, архитектура, data plane, ingest, статический /
архивный / динамический анализ, безопасность, наблюдаемость, развёртывание,
миграция, тестирование, форматы, ограничения, план реализации, тестирование
инференса LLM).

Здесь описан **процесс**: что подать на вход, что происходит на каждом шаге, как
читать ленту, что может пойти не так и как проверить результат. Числа — из прогона
на локальной модели `Qwen3.8-27B-UD-Q5_K_XL` (`runner=local`, Docker недоступен).

---

## 0. Что получится на выходе

Один прогон даёт:

- **модель архитектуры** (`data/models/<имя>.json`) — узлы и связи по всем
  аспектам, каждый узел с `evidence` (файл-источник) и признаком `code`/`docs`;
- **полный журнал прогона** (события: что собрано, сколько узлов, какие ремонты);
- **отчёт сверки** по аспектам (сколько элементов без связей, без evidence);
- запись о прогоне в проекте (история, привязка к модели).

Модель дальше используется как обычно: просмотр по нотации C4, аспектные виды,
валидация, пакет передачи, кодогенерация, приёмка по графу.

## 1. Подготовка

### 1.1. Что нужно

| Что | Значение в примере | Примечание |
|---|---|---|
| Репозиторий | `https://github.com/pol4/MLScan.git` | URL (клонируется) или локальный путь |
| Документация | `Arch_v3/*.md` внутри репозитория | попадает во **второй проход** |
| LLM | `http://192.168.20.20:8000/v1`, `Qwen3.8-27B-UD-Q5_K_XL` | настраивается в `⚙ Setup` |
| Агент | `builtin` (встроенный) | внешний CLI-агент — для кодогенерации |
| Runner | `local` (или `docker`, если демон поднят) | влияет на изоляцию, не на логику |
| Бюджет сессии | 60 000 символов | `Session context budget` |

### 1.2. Настройки, которые важны для «всех аспектов»

- **LLM mode = live** (иначе прогон пойдёт на мок-фикстуре).
- **Compare with documentation = вкл** — иначе документация `Arch_v3` не будет
  использована (второй проход).
- **Extract aspects = вкл**, **aspect passes = вкл**.
- **Список аспектов** (порядок важен, каждый — отдельный проход):
  `data → interface → behavior → process → deployment → access → quality`.
- **Session context budget** — потолок одной сессии; при переполнении старые
  обмены отбрасываются, а материал (исходники) сохраняется.

Все это — `⚙ Setup` (`R`) в UI, либо `PUT /api/config`:

```bash
curl -X PUT http://127.0.0.1:8000/api/config -H 'Content-Type: application/json' -d '{
  "llm": {"mode": "live"},
  "agent": {"runner": "local"},
  "context": {"compare_docs": true, "aspect_passes": true, "reconcile_report": true}
}'
```

## 2. Запуск

### Через UI

1. `⚙ Setup` — проверить LLM, агента, бюджет, включить сравнение с документацией.
2. Нижняя панель → вкладка **`Projects`** → поле адреса репозитория → **Reconstruct
   graph**.
3. Панель сама переключится на **`Events`** — там идёт журнал.

### Через API

```bash
curl -X POST http://127.0.0.1:8000/api/projects -H 'Content-Type: application/json' \
     -d '{"name":"MLScan","repo":"https://github.com/pol4/MLScan.git"}'

curl -X POST http://127.0.0.1:8000/api/reconstruct -H 'Content-Type: application/json' \
     -d '{"repo":"https://github.com/pol4/MLScan.git","agent":"builtin","project":"MLScan"}'
# → {"run_id": "…"}
```

Прогон асинхронный: `POST` сразу отдаёт `run_id`, работа идёт в фоне.

## 3. Что происходит по шагам

Ниже — реальная последовательность событий прогона MLScan.

### Шаг 0. Резолв репозитория

```
run started for `https://github.com/pol4/MLScan.git`
resolving repository (cloning if it is a URL)…
repository ready: MLScan
```

URL клонируется во временный каталог; локальный путь берётся как есть.

### Шаг 1. Сбор исходников и сжатие контекста

```
collecting source files…
collected 287 source files; compressing context…
pass 1/2 - source code: 287 files, 1394544->107779 chars
```

Из 287 файлов собрано ~1,39 млн символов; стратегия `extract` сжала материал до
~108 тыс. символов (файлы без полезной архитектурной информации отсеиваются).

### Шаг 2. Базовый проход по коду (pass 1/2)

```
opening the in-process agent session (one conversation for the whole run)
code: request sent to the agent session
session context trimmed: 136378 → 60000 chars (budget 60000)
calling the LLM (Qwen3.8-27B-UD-Q5_K_XL); up to 3 repair attempt(s)
refining graph (1/3) to fix 3 issue(s)
refining graph (2/3) to fix 1 issue(s)
validated graph: 39 nodes, 43 edges, ok
```

- Одна сессия на весь прогон: материал отправляется **один раз**, дальше — короткие
  сообщения в том же диалоге.
- Контекст обрезан до бюджета (60 000) — при этом **исходники сохраняются**
  (обрезается хвост старой переписки, а не материал).
- Модель вернула граф, валидатор нашёл нарушения схемы (якоря, типы связей) — два
  раунда ремонта, на третьем граф валиден: **39 узлов / 43 связи**.

### Шаг 3. Аспектное извлечение (структурная опора)

```
aspect-aware extraction: 1407 nodes
aspect extraction skipped 9 element(s) with no valid anchor: Task(_task_priority), …
```

Из кода механически извлекаются элементы с валидным якорем (операции, интерфейсы,
сущности данных и т.п.) — **1407 узлов**. Это «скелет», к которому будут
привязываться аспектные проходы. 9 элементов пропущено: у них нет допустимого
родителя по метамодели (внутренние `Task`-обёртки) — это нормально, а не ошибка.

### Шаг 4. Семь аспектных проходов

Каждый аспект — **отдельный запрос** в той же сессии: для него выбираются только
релевантные файлы, в промпт кладётся фрагмент графа (свои элементы + типы, к
которым можно привязаться), модель возвращает **только элементы этого аспекта**,
они вливаются в граф.

| Аспект | Файлов выбрано | Прирост (прогон 2) | Прирост (прогон 1) |
|---|---|---|---|
| `data` | 140 | **+51 узел, +42 связи** | +3 узла, +0 связей |
| `interface` | 102 | +0 узлов, +0 связей | +0 узлов, +0 связей |
| `behavior` | 6 | **+73 узла, +73 связи** | +24 узла, +32 связи |
| `process` | 102 | **+41 узел, +53 связи** | +39 узлов, +13 связей |
| `deployment` | 155 | **+10 узлов, +17 связей** | +0 (см. §5.2) |
| `access` | 52 | **+21 узел, +7 связей** | +18 узлов, +11 связей |
| `quality` | 34 | **+26 узлов, +26 связей** | +48 узлов, +48 связей |

Разброс между прогонами — нормальная вариативность модели: состав элементов
фиксирует метамодель и enforcement, а не температура генерации.

Пример ленты по аспекту:

```
aspect pass `behavior`: reconstructing…
aspect `behavior`: 6 relevant source file(s) selected
aspect:behavior: request sent to the agent session
refining graph (1/3) to fix 1 issue(s)
validated graph: 53 nodes, 51 edges, ok
aspect `behavior`: +24 nodes, +32 edges
```

Важно: `+0 узлов` у `interface` — это **нормальный результат**, а не сбой: интерфейсы
и операции уже пришли из базового прохода (в графе 136 `Interface` и 1090
`Operation`). Аспект «уже покрыт».

### Шаг 5. Отчёт сверки

```
reconciliation: 123 element(s) without relationships, 0 without evidence —
  `data`: 89 orphan(s), 0 without evidence; `process`: 31 orphan(s), 0 without evidence;
  `structure`: 2 orphan(s), 0 without evidence
```

Сверка показывает, где модель «дырявая»: элементы без связей. `0 without evidence`
означает, что у **каждого** узла есть источник. Если отчёт включён в режиме
исправления (`reconcile_fix`), агент отдельным проходом достраивает связи.

### Шаг 6. Второй проход по документации и слияние (pass 2/2)

```
collecting documentation…
pass 2/2 - documentation: 132 files; comparing
docs: request sent to the agent session
refining graph (1/3) to fix 4 issue(s)
validated graph: 28 nodes, 54 edges, ok
merged code + docs: 1562 nodes, 1482 edges, 1557 node deviation(s) flagged
```

Документация (`Arch_v3` + прочие `*.md`) читается отдельным проходом и **сливается**
с моделью из кода. Расхождения помечаются: узел, который есть в документах, но не
подтверждён кодом (или наоборот), получает признак источника.

### Шаг 7. Сохранение

```
model saved: MLScan.json (9a889a2897d5e724)
```

Модель сохранена, прогон привязан к проекту, статус `done`.

## 4. Как читать ленту

| Событие | Смысл |
|---|---|
| `status … collecting/collected N source files` | сбор и сжатие материала |
| `pass 1/2 - source code: N files, X->Y chars` | базовый проход: сколько осталось после сжатия |
| `session context trimmed: X → Y` | обрезка контекста сессии до бюджета |
| `calling the LLM (модель); up to N repair attempt(s)` | запрос к модели |
| `refining graph (k/N) to fix M issue(s)` | раунд ремонта: валидатор нашёл M нарушений |
| `validated graph: N nodes, M edges, ok` | ответ модели прошёл схему |
| `aspect-aware extraction: N nodes` | структурный скелет из кода |
| `aspect pass \`X\`: reconstructing…` | начало аспектного прохода |
| `aspect \`X\`: N relevant source file(s) selected` | сколько файлов попало в проход |
| `aspect \`X\`: +n nodes, +m edges` | вклад аспекта |
| `reconciliation: … orphan(s)` | сверка: элементы без связей / без evidence |
| `merged code + docs: N nodes, M edges` | итог слияния кода и документации |
| `error validation (k/N): …` | нарушение схемы с текстом причины |
| `error aspect … skipped/failed/rejected` | аспект пропущен (нет якоря / пустой ответ / невалидный граф) |

## 5. Что может пойти не так (и что делать)

Все случаи ниже — из реального прогона.

### 5.1. «Элементы без валидного якоря»

```
aspect extraction skipped 9 element(s) with no valid anchor: Task(_task_priority), …
```

Метамодель разрешает `Task` только внутри `Process/Activity`. Внутренние функции
`_task_*` не привязываются — они и не должны. **Действие:** ничего; если элементов
много, проверьте, не попал ли в материал нерелевантный код.

### 5.2. Пустой ответ модели на аспекте (исправлено и проверено)

Первый прогон:

```
aspect `deployment`: 155 relevant source file(s) selected
session context trimmed: 134722 → 509 chars (budget 60000)      ← аномалия
validation (1/4): the model returned an empty graph (no `nodes`)
aspect `deployment`: +0 nodes, +0 edges
```

Симптом: обрезка контекста даёт **аномально маленькое** число (сотни символов вместо
десятков тысяч), и модель отвечает пустым графом. Причина: аспектный промпт несёт
свои исходники и приходит **последним** сообщением; старая логика обрезки считала
хвост «мусором» и выбрасывала материал, оставляя заголовок промпта.

**Исправлено**: обрезка сохраняет **материал** (вступительные исходники) и
**новейший запрос**, отбрасывая только середину переписки. Второй прогон:

```
aspect `deployment`: 155 relevant source file(s) selected
session context trimmed: 133888 → 60000 chars (budget 60000)     ← норма
aspect `deployment`: +10 nodes, +17 edges
```

**Как проверить у себя:** после `session context trimmed` число должно быть близко к
бюджету (десятки тысяч), а не сотни символов.

### 5.3. Элемент не того аспекта

```
aspect `deployment` skipped 1 element(s): unknown-system (type System is not part of `deployment`)
```

Модель вернула элемент, которого нет в списке типов аспекта. Он отбрасывается, проход
продолжается. **Действие:** ничего, если единичные случаи.

### 5.4. Аспект «уже покрыт»

```
aspect `interface`: +0 nodes, +0 edges
```

Не сбой: элементы аспекта уже есть в графе из базового прохода. Именно поэтому
порядок аспектов и базовый проход важны — база даёт «скелет», аспекты дополняют.

### 5.5. Много замечаний валидатора в аспекте

```
refining graph (1/3) to fix 30 issue(s)
```

`process` дал 30 замечаний (в основном якоря и типы связей), но после раунда ремонта
граф стал валидным. Если раунды исчерпаны и граф невалиден, аспект **отклоняется**
целиком (`rejected (invalid graph)`) — граф не портится, вклад аспекта теряется.

### 5.6. Дубликат id после слияния кода и документации (исправлено)

Второй прогон завершился статусом **`invalid`**:

```
merged code + docs: 1676 nodes, 1655 edges, 1674 node deviation(s) flagged
model saved: MLScan.json (60f964cd45d219c9)
error graph failed validation: duplicate node id: actor://operator
```

Слияние сопоставляло элементы по «тип + имя», а не по id: элемент из документации с
**тем же id**, но чуть другим именем (`Operator` против `Operator (docs)`) попадал во
вторую запись — и в графе оказывались два узла с одним id.

**Исправлено**: слияние сопоставляет по **id** (id — стабильный URI), а в конце
гарантирует уникальность id в результате. Итоговый граф валиден.

**Как проверить у себя:** после `merged code + docs` не должно быть
`error graph failed validation`; статус прогона — `done`, а не `invalid`. Если статус
`invalid` — откройте `Validation`, там будет конкретная причина.

### 5.7. Дыры в модели (orphans)

`reconciliation` показывает элементы без связей (`data: 89 orphan(s)`). Это не
ошибка, а карта неполноты. **Действие:** включить `reconcile_fix`, чтобы агент
достроил связи по источникам, либо добить вручную в инспекторе.

## 6. Проверка результата

1. **Валидация** — нижняя панель → `Validation` → **Check**: схема и ограничения.
2. **Отчёт** — `📊 Report`: по аспектам, покрытие требований, метрики.
3. **Просмотр** — граф по нотации C4: человек — стик-фигура, внешняя система —
   штриховая рамка, хранилище — цилиндр, контейнер — с шапкой; связи идут от
   границы к границе, со стрелкой и подписью типа.
4. **Аспектные виды** — линза аспекта (`state`, `er`, `bpmn`, `sequence`, `api`…).
5. **Срезы и уровни** — `L1…L4`, поиск узла, фокус на элементе.
6. **Приёмка** — для результата кодогенерации: `arch-diff` (граф-дифф «цель ↔
   результат») с вердиктом.
