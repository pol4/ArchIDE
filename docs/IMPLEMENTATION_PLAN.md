# ArchIDE — план реализации (по ROADMAP)

Декомпозиция фаз `ROADMAP.md` на задачи с критериями готовности. Каждая задача:
**цель → изменения → тесты → готово, когда**. Статусы: ✅ сделано · 🔄 в работе ·
⬜ запланировано.

Правила работы — `../AGENTS.md` (после крупных доработок прогон `tests/run_e2e.sh`;
новая функциональность ⇒ новые тесты API + браузер и синхронизация `SCENARIOS.md`).

**Принцип (Concept §0.1, «динамическая устойчивость»):** мы не строим «идеальную»
онтологию заранее — базовая графовая модель **легко расширяема** и может быть
неполной, а её непротиворечивость **поддерживается динамически** агентом
(наблюдение → расхождение → коррекция). В плане это реализуют **Ф4.9** (ревьюер
после ручных правок) и **Ф4.10** (Reconciler); сигналы наблюдения дают Ф2.1–Ф2.4
(валидация/покрытие) и Ф4.1–Ф4.4 (транзакции/impact).

### Порядок задачи: тесты — ДО реализации (обязательно)

Для **каждой** задачи **сначала добавляются тесты** (API и браузерные, где применимо),
фиксирующие ожидаемое поведение новой функциональности, и только **затем** пишется
реализация. Задача **не считается готовой**, пока новые тесты не зелёные и сквозной
`tests/run_e2e.sh` не проходит. Колонка **«Тесты (до реализации)»** в таблицах ниже —
это тесты, которые должны быть добавлены **до** реализации (они падают «red» до неё).

Если функциональность пока не имеет UI-поверхности, браузерный тест не добавляется,
но это **явно фиксируется**; при появлении поверхности тест добавляется до реализации.

### Ключевое требование UI

**1. Несколько аспектов одновременно.** Для полноты понимания модели нужно **видеть
несколько аспектов одновременно**, а не только переключаться между ними: режимы
«tabs» (один аспект), «split» (несколько панелей рядом), «overlay» (аспекты поверх
структуры на одной канве) с общим фокусом/уровнем и кросс-аспектной подсветкой.

**2. Диалог с агентом как основной сценарий работы с графом.** Вместо ручного
редактирования в UI пользователь **поручает изменения агенту в режиме чата**. Агент:

- переводит намерение пользователя в **транзакцию правок** графа;
- **задаёт уточняющие вопросы** при неоднозначности;
- **предупреждает о проблемах** предлагаемых изменений (impact, нарушения инвариантов,
  потеря покрытия требований);
- формирует **семантический диф** на подтверждение;
- после подтверждения применяет правку и **сразу дорабатывает другие части графа**,
  чтобы он **не потерял консистентность** (referential actions, авто-починка, gate);
- по запросу создаёт **нестандартные аспекты, срезы и представления** «на лету».

**3. Ручное редактирование сохраняется.** Человек по-прежнему может **вручную** править
граф и его аспекты в UI (канвас/формы/грид) — это не отменяется. После ручных правок
**агент проверяет граф**, находит нарушения целостности/покрытия и **предлагает
исправления** (семантический диф на подтверждение). Оба режима — чат и ручной —
сосуществуют, и оба проходят через один gate согласованности.

**Нотация C4 (по замечанию 27.10):** элементы рисуются по своей нотации — человек/роль стик-фигурой, система с шапкой и толстой рамкой, внешняя система штриховой рамкой, контейнер с цветной шапкой, хранилище цилиндром, узел развёртывания двойной рамкой; под элементом — `[Kind]` в нотации C4. Связи идут **от границы к границе** (раньше из центра — их скрывали элементы), толще, со стрелкой и подписью типа связи на плашке в отдельном верхнем слое. Широкий уровень переносится в несколько подстрок — граф больше не растягивается в 60 000px полосу, которую «fit» сжимал в линию. 5 браузерных проверок `C4 …`.

**Раскладка графа:** узлы в строке упорядочены **под родителем** (было — по алфавиту), поэтому связи идут вниз, а не крестят канвас; подписи связей разносятся по кривой, чтобы не накладываться. Слияние кода и документации сопоставляет элементы **по id** (не по «тип+имя») и гарантирует уникальность id в результате — иначе граф падал с `duplicate node id` и прогон получал статус `invalid`.

**Реальный прогон (MLScan/Arch_v3):** полная реконструкция по всем аспектам, инструкция — `RECONSTRUCTION_GUIDE.md`. Прогон вскрыл регрессию обрезки контекста: материал вытеснялся из сессии, аспект `deployment` получил пустой промпт и вернул пустой граф. Исправлено: `_fit` сохраняет материал и новейший запрос, отбрасывая только середину переписки (3 проверки `fix(7b)`).

**Ревью (7 предупреждений исправлено):** (1) `save_model` больше не удаляет посторонний файл — очистка legacy `<name>.git.json` вынесена в явную миграцию `model_store.migrate_legacy_names` (только переименование, вызывается один раз на старте сервера); (2) в `graphdiff` scope реально ограничивает вердикт — `changed` и покрытие требований считаются по элементам внутри среза; (3) команда чата «расширить аспекты» передаёт репозиторий проекта (а не имя модели) и внятно отказывает, если репозитория нет; репозиторий теперь записывается в проект при запуске (`attach_run(..., repo)`); (4) внешнему CLI-агенту кодогенерации передаётся минимальное окружение вместо всего `os.environ`; (5) шаблоны сохраняют регистр имени модели — id-пространства скаффолда и UI совпадают; (6) создание проекта переключает на него и очищает холст предыдущей модели; (7) `_fit()` действительно укладывается в бюджет контекста.

**Проверка (Ф8.5):** сквозной браузерный обход **W1–W6** (проект → реконструкция → инспектор и линза → валидация → отчёт → пакет передачи) в общем наборе; по ходу найден и исправлен баг: новый проект не появлялся в панели **Projects** до повторного открытия.

**Сделано (Ф8.5):** старт «с нуля» в пару шагов. Каталог шаблонов (`backend/templates.py`): **web service**, **service + database**, **CLI**, **blank** — каждый даёт **валидную стартовую модель** (C4-каркас + типовые аспекты: интерфейсы/операции, данные, состояния, роли, развёртывание), проверенную `validate_graph`. **Сделано (Ф8.4):** если в репозитории **нет кода, но есть документы** (ТЗ/требования), базовый проход работает в **design mode** — архитектура **проектируется по документации** (`build_design_prompt`: «DESIGNING the architecture … there is no source code yet»), документы идут как материал прохода, сравнение с документацией (pass 2) в этом режиме не дублируется; отключается флагом `context.design_from_docs`. Пустой репозиторий (ни кода, ни документов) падает с понятной ошибкой.

**Сделано (Ф8.2):** кодогенерацию можно отдать **произвольному внешнему CLI-агенту**: `codegen.mode=cli` + `codegen_cli.command` (шаблон с `{workdir}`/`{prompt_file}`) — агент запускается как команда в свежем рабочем каталоге, получает задание файлом `TASK.md` (work package + спецификации + метки), а всё, что он написал, становится **репозиторием результата**; фиксируются `exit_code`, `cli.log` и коммит, сбой агента **сообщается**, а не принимается молча. **Сделано (Ф8.2b):** кодогенерация стала устойчивой — невалидный ответ агента **повторяется** с ремонтным промптом (`retries` в ответе), а размер ответа ограничен бюджетами (`codegen.max_files`, `max_file_chars`, `max_total_chars`): слишком большие файлы и лишние пропускаются с **причиной** (`skipped: [{path, reason}]`), что видно в ответе и в панели.

**Сделано (Ф8.3b):** приёмка стала точной — сопоставление идёт по слоям **id → метки/evidence → тип+имя** (`matched_by` в отчёте показывает, чем именно сопоставлено), вердикт **скоупится**: с `scope` (узел) приёмку решают только элементы **внутри среза**, остальные — информационно (`missing_in_scope`), и добавлен **вердикт по требованиям** (`requirements.total/covered/uncovered`). **Сделано (Ф3.11):** у непрерывной сессии появился **бюджет контекста** (`llm.max_context_chars`, поле в мастере настройки, по умолчанию 60k символов, 0 = без ограничения): перед каждым запросом история подрезается — сначала отбрасываются самые старые обмены, затем ограничивается первое сообщение с исходниками, и в ленту пишется `session context trimmed: X → Y chars`. **Сделано (Ф10.1):** `backend/projects.py` — проект как владелец графа, репозиториев, прогонов, чата и документов (`data/projects/<id>.json`); API `GET/POST /api/projects`, `GET/PUT /api/projects/<id>`, `POST /api/projects/<id>/{open,chat,view}`; реконструкция принимает `project` и **привязывает к нему модель и прогон**; существующие модели **мигрируют** в проекты автоматически (при листинге и при открытии по имени модели).

**Сделано (Ф10.4):** из мастера `⚙ Setup` убраны поле репозитория и кнопка «Reconstruct graph» — панель стала «1 · Defaults» (только **агент по умолчанию**, LLM, бюджет контекста, том); запуск реконструкции — во вкладке **Projects** нижней панели (и, далее, из чата в Ф10.5), агент по умолчанию из мастера подставляется в запуск. **Сделано (Ф10.5):** чат понимает команды — `reconstruct <repo>` (реконструкция в текущий проект), `add aspect <имя>` / `rebuild aspects <a,b>` (**дообогащение модели аспектами** через прогон с `model`+`aspect_list`), `проверь модель` (формальная валидация с результатом в ленте), `примени` (применить ответ агента транзакцией) и ранее — `add/remove/review/fix`. Долгие и структурные команды **предлагаются** («…? reply «да» to run») и выполняются после подтверждения (`да`/`ок`/`confirm`), отмена — `нет`; запущенный прогон уходит во вкладку **Events**.

**Сделано (Ф10.6):** в нижней панели появилась вкладка **Validation** — явная поверхность валидации: **Check** (формальная валидация + нарушения ограничений), **Check with agent** (агентный разбор модели: issues по видам + предложенные исправления), **Propose fixes** и **Apply fixes** (применение предложений **транзакцией** с перезагрузкой модели и повторной проверкой), плюс история проверок и сводка; команды доступны из палитры `⌘K` и из инспектора элемента («Validate model…»).
