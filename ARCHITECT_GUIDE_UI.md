# ArchIDE — пошаговый гайд архитектора (только через UI)

Практическое руководство со скриншотами: оба сценария **из интерфейса**, без командной
строки. Дополняет `ARCHITECT_GUIDE.md` (те же шаги с curl и API-шпаргалкой).
Интерфейс построен по принципу **«граф прежде всего»**: канвас занимает весь экран, а
аспекты, правки и операции открываются **от самого элемента**; всё остальное — по
требованию (мастер, панели, палитра, отчёты).

- **Сценарий A** — изучить готовый репозиторий, внести и проверить архитектурные
  изменения, собрать задания для агента кодирования, принять результат по графу.
- **Сценарий B** — спроектировать приложение с нуля, сгенерировать артефакты, передать их
  агенту кодогенерации и проверить полученный репозиторий по графу.

Скриншоты сняты на моделях `ArchIDE` (443 узла) и `TripApproval` (55 узлов, все аспекты).
Пересобрать их: `tests/browser/capture_screens.mjs` и `capture_screens_tail.mjs`.

## 0. Запуск и как устроен экран

```bash
cd archide-poc && python3 server.py      # UI и API: http://127.0.0.1:8200
```

Откройте `http://127.0.0.1:8200` — вы увидите **только граф**: панели скрыты, снизу узкая
полоса событий.

![Общий вид](docs/screens/01-overview.png)

**Верхняя панель:** `☰` — показать/скрыть панели, `◐` — тема (тёмная/светлая), `⌘K` —
командная палитра, `🤖 Agent` — чат с агентом, `⚙ Setup` — мастер настройки, `📊 Report` —
отчёт. **Тулбар над канвасом:** крошки (уровень вложенности), фильтр источников (код/доки),
селектор уровня C4, слои `↑`/`↓`, поиск узла, зум `−`/`+`/`⌂`, `⤓ all` — экспорт всех
аспектных видов одним SVG, `＋` — создать узел, `⧉` — открыть окно аспекта.

**Горячие клавиши:** `Ctrl/⌘+K` — палитра, `A` — аспект-линза выделенного элемента,
`E` — правка, `Space` — чат с агентом, `R` — мастер настройки, `,`/`.` — листать вид
аспекта, `Esc` — назад/закрыть. Состояние (модель, линза, уровень, тема, панели)
**сохраняется** между перезагрузками.

**Модели** лежат в `archide-poc/data/models/<Имя>.json` и открываются полем *Model name* →
**Load** (панели: `☰`).

## Сценарий A. Готовый репозиторий

### A1. Реконструкция

> Разбор реального прогона по всем аспектам (MLScan + `Arch_v3`) — в
> [`RECONSTRUCTION_GUIDE.md`](RECONSTRUCTION_GUIDE.md): что происходит на каждом шаге,
> как читать ленту, что может пойти не так, метрики и артефакты.

1. `⚙ Setup` (или `R`) — мастер настроек: LLM-подключение, агент, том агента и
   **бюджет контекста сессии** (`Session context budget`, по умолчанию 60 000 символов):
   длинный прогон подрезает старые обмены, чтобы не упасть с «model ran out of context
   space»; в ленте видно `session context trimmed: X → Y`. **Запуска реконструкции здесь
   больше нет** — мастер только настраивает.

![Мастер настройки](docs/screens/08-setup.png)

2. Запуск — из нижней панели **`Projects`** (или командой `reconstruct <репозиторий>` в
   чате): укажите адрес репозитория/URL и нажмите **Reconstruct graph**. Нижняя панель
   переключится на **`Events`** и покажет ход: сбор файлов, C4-проход, аспектное извлечение,
   затем **последовательные аспектные проходы** (`aspect `data`: +N nodes…`) и отчёт сверки.

![Реконструкция](docs/screens/13-reconstruct.png)

> На скриншоте профиль `mock` (детерминированный граф без LLM) — интерфейс и ход событий в
> `live`-режиме те же.

### Как устроен экран (Ф10/UI)

Экран собран вокруг одной идеи: **граф — внутренняя структура, а архитектор работает
с C4 и аспектами как с отдельными представлениями.**

- **Подзакладки канваса** (`C4 | Processes | Data | States | Interfaces | Deployment |
  Access | Quality | Aggregation | Crosscutting`) — переключатель представления.
  **C4** — основная схема (структурные элементы: система, контейнер, компонент,
  внешняя система). Остальные подзакладки показывают **только свой аспект** для
  выбранного элемента — это не «слои поверх C4».
- **Дерево сущностей C4** слева (`🗂 tree`) — навигатор вроде дерева проекта в IDE:
  система → контейнеры → компоненты. Клик по элементу выбирает его для активной
  подзакладки; дерево сворачивается кнопкой и тянется за правую грань.
- **Раскладка канваса** (подзакладка, справа): `C4 layers` / `Grid` / `By aspect` +
  **⤢ auto** — автоматическая расстановка; **↺** — забыть сохранённую. **Элементы
  можно перетаскивать мышью**: позиция запоминается для модели
  (`data/layouts/<модель>.json`) и восстанавливается при следующем открытии.
  После ручного перетаскивания сохраняется именно ручная расстановка.
- **Ресайз панелей**: нижняя панель — за верхнюю грань; левые панели (сайдбар
  настроек, дерево C4) — за правую грань. Размеры запоминаются.
- **Чат агента** — вкладка **Agent** в нижней панели (отдельной кнопки в верхней
  панели нет). **Загрузка/экспорт модели** — во вкладке **Projects** (проектное
  управление), а не в панели канваса.

### Нотация C4 (как читать граф)

Элемент рисуется по своей **нотации**, а не одинаковыми прямоугольниками:

| Что | Как выглядит | Подпись |
|---|---|---|
| Человек (Person, Role, Actor) | стик-фигура | `[Person]` |
| Система (System) | рамка потолще + цветная шапка | `[Software System]` |
| Внешняя система (ExternalSystem) | **штриховая** рамка | `[External System]` |
| Контейнер (Container) | цветная шапка | `[Container]` |
| Компонент (Component, Module) | рамка + цветная полоса | `[Component]` |
| Хранилище/данные (DataStore, DataEntity) | **цилиндр** | `[Database]` |
| Узел развёртывания (Node, Runtime) | двойная рамка | `[Deployment Node]` |
| Интерфейс/операция | рамка | `[Interface]` |

Цвет рамки — аспект элемента; строка `source: code/docs` внизу — откуда элемент
взят. Связи идут **от границы к границе** (а не из центра, где их скрывали
элементы), рисуются толще, со стрелкой и **подписью типа связи** на плашке поверх
графа. Широкий уровень переносится в несколько подстрок — граф не растягивается в
полосу, которую «fit» сжимал бы в линию.

### A2. Изучение: всё — от элемента

Выберите элемент (в дереве слева или кликом на канвасе), затем переключайте
подзакладки: `Data` покажет данные этого элемента, `States` — его состояния,
`Interfaces` — интерфейсы. Кадр: дерево C4 и подзакладка аспекта.

![Дерево C4](docs/screens/19-tree.png)

![Подзакладка аспекта](docs/screens/20-views.png)

![Автоматическая раскладка](docs/screens/21-layout.png)

**Кликните любой элемент** — справа откроется **инспектор**: свойства (id, родитель,
evidence, описание), **чипы аспектов**, в которых элемент участвует (с количеством), и
действия.

![Инспектор элемента](docs/screens/02-inspector.png)

**Клик по чипу аспекта** — весь канвас переключается в **нотацию этого аспекта**
(аспект-линза): состояния, BPMN, ER, последовательности, C4, дерево развёртывания, таблицы.
Сверху — полоса линзы: аспект, элемент, селектор вида и **«← к C4»**.

![Аспект-линза: состояния](docs/screens/03-lens-state.png)

![Аспект-линза: тот же аспект в виде графа](docs/screens/04-lens-graph.png)

Дополнительно: **двойной клик** по узлу — внутрь (следующий уровень); селектор **уровня C4**
показывает уровень целиком; **поиск узла** находит элемент, включает нужный аспект и
выделяет его.

![Уровень целиком](docs/screens/10-level.png)

![Поиск узла](docs/screens/11-search.png)

### A3. Изменение архитектуры

Всё делается **от элемента** (инспектор): **Rename**, **Create inside** (дочерний элемент
нужного типа), **Link** (связь с другим узлом), **Delete**. Любая правка идёт транзакцией с
валидацией, referential actions и защитой от гонок (409) и прав (403).

Создание «постороннего» элемента — **клик по пустому месту канваса** (поповер «создать
здесь»). Массовые операции — из **палитры** `⌘K`: *Impact*, *Review*, *Reconcile
(apply fixes)*, *Validate*, *Metrics*, *Coverage*.

![Командная палитра](docs/screens/05-palette.png)

### A4. Валидация и метрики

`📊 Report` — полноэкранный отчёт: валидация (инварианты, якоря, кросс-аспектные правила),
метрики по аспектам (элементы, покрытие объявленных типов, сироты, элементы без evidence),
покрытие требований и — если задана модель-результат — **вердикт приёмки**.

![Отчёт](docs/screens/07-report.png)

### A5. Комплект для агента кодирования

Панели `☰` → панель **9 · Architect scenario** (или команды палитры): *Work package*
(срез + критерии приёмки), *Markers* (подписанные метки трассируемости), *Coverage matrix*,
*Conformance*, *Generate artifacts & package* (OpenAPI/DDL/JSON Schema/скелеты).
Кнопка **Download handoff package (.tar.gz)** собирает всё это в **один архив** для агента:
`manifest.json` (модель, хеш, состав, проверка меток), `workpackage.json`, `artifacts/`,
`markers.json` и `README.md` с инструкцией (в том числе требование вставить метки в код).

![Панели операций: work package](docs/screens/09-panels.png)

### A6. Передача агенту кодогенерации

В панели **9** (или из палитры) задайте *Codegen target* — имя репозитория результата — и
нажмите **Code generation**: агент получает work package, спецификации и метки, а возвращает
**новый репозиторий** (файлы в `data/generated/<имя>`, изменения коммитятся). В окне —
путь, список файлов и коммит.

![Кодогенерация](docs/screens/14-codegen.png)

### A7. Приёмка результата по графу

1. Реконструируйте полученный репозиторий (мастер `⚙ Setup`, путь
   `data/generated/<имя>`) — получится модель результата.
2. В панели **9** нажмите **Diff vs result model** — вердикт (`ok`/`gaps`), сводка
   (target/result/matched/missing/extra/coverage) и разбивка по аспектам; тот же вердикт
   попадает в `📊 Report`.

![Приёмка по графу](docs/screens/15-acceptance-diff.png)

## Сценарий B. Разработка с нуля

1. **Начните с шаблона**: палитра (`⌘K`) → *New model from template…* (или нижняя панель
   **Projects** → *From template…*). Выберите форму системы — **Web service**,
   **Service + database**, **CLI** или **Blank** — и задайте имя: ArchIDE сразу создаёт
   **валидную стартовую модель** (C4-каркас плюс типовые аспекты: интерфейсы и операции,
   данные, состояния, роли, развёртывание) и открывает её в графе. Дальше — обычные правки.
   Нужен полностью ручной старт — берите **Blank** и добавляйте узлы на канвасе (`＋`,
   в инспекторе — *Create inside* / *Link*), либо `Import` готового файла модели.

![Модель из шаблона](docs/screens/17-template.png)
2. **Проверьте**: `📊 Report` (валидация, метрики по аспектам, покрытие требований).
3. **Соберите артефакты и задания**: панель **9** (или палитра) — *Work package*,
   *Markers*, *Coverage matrix*, *Generate artifacts & package*.
4. **Передайте агенту кодогенерации**: *Code generation* (как в A6).
5. **Примите результат по графу**: реконструируйте репозиторий результата и нажмите
   *Diff vs result model* (как в A7). При расхождениях правьте модель и повторяйте.

## Сценарий C. Синтез архитектуры по описанию (Ф11)

Случай, когда кода ещё нет: архитектура **проектируется по постановке**, которую
архитектор формулирует прямо в чате.

1. **Опишите систему в чате.** Откройте вкладку **Agent** и напишите постановку
   командой `design …` (или `синтез …`). Агент покажет подтверждение и длину описания.

![Постановка в чате](docs/screens/22-synthesis-chat.png)

2. **Подтвердите** («да») — запускается **синтез**: описание (и приложенные
   документы, если они загружены) становится материалом проектировочного прохода.
   В ленте видно `no source code: designing the architecture from N document(s)`.
3. **Получите граф.** По завершении модель загружается в канвас; дальше с ней
   работают как обычно — подзакладки аспектов, дерево C4, валидация.

![Синтезированный граф](docs/screens/23-synthesis-graph.png)

4. **Выгрузите архитектурную документацию** — кнопка **Documentation** во вкладке
   **Projects** (или палитра `⌘K`): Markdown с обзором, декомпозицией C4, разделом по
   каждому аспекту, связями, требованиями и трассируемостью (evidence). Документ
   генерируется **из модели**, поэтому не расходится с ней.

![Документация](docs/screens/24-documentation.png)

Аспектные подзакладки показывают свою часть той же модели (данные — цилиндрами):

![Аспект синтезированной модели](docs/screens/25-synthesis-aspect.png)

**Реальный прогон** (живая модель `Qwen3.8-27B`, `runner=docker`): по приведённому выше
абзацу описания получено **112 узлов / 90 связей** за ~20 минут, вклад дали **все семь
аспектов** (`data` +13, `interface` +18, `behavior` +11, `process` +14, `deployment` +4,
`access` +14, `quality` +6), у **100 %** узлов есть `evidence`. В графе — контейнеры
(веб-приложение, сервис согласования, брокер, воркер уведомлений), внешние системы
(1С, почтовый шлюз) со штриховой рамкой, роли и права (бухгалтер, администратор,
управление ролями), процессы (бронирование, учёт расходов), состояния заявки и
требования (согласование за два рабочих дня, аудит действий). Архитектурная
документация по этой модели — ~35 000 символов, 6 разделов; пакет для
кодогенерирующего агента — манифест, work package, маркеры, `schema.sql`,
`openapi.yaml`, `skeleton.py`.

5. **Передайте пакет кодогенерирующему агенту** — как в сценарии A5/A6 (handoff
   собирает work package, артефакты, метки и критерии приёмки из той же модели).
6. **Скорректируйте результат** — двумя способами:
   - **визуально**: перетащите элементы (раскладка запоминается), правьте через
     инспектор (`Create inside`, `Link`, `Delete`), добавляйте узлы (`＋`);
   - **через агента**: команды в чате (`add Component … under …`, `remove …`,
     `проверь модель`, `fix`) — правки идут той же транзакцией с валидацией.

> Постановка формулируется свободным текстом; чем конкретнее роли, данные,
> внешние системы и процессы — тем полнее получится граф. Документы с требованиями
> можно приложить в чате (**Attach**) или загрузить заранее — они попадут в RAG и
> в материал синтеза.
>
> Скриншоты этого сценария сняты на **живом прогоне** (`runner=docker`, локальная
> модель), а не в mock-режиме, поэтому на них настоящая архитектура.

## Чат с агентом

`🤖 Agent` (или `Space`) открывает вкладку **`Agent` в нижней панели** (вкладки
`Events | Agent | Projects | Validation`). Сверху — **строка контекста**: что выделено, какая
линза активна, какая модель. Через чат можно не только править модель, но и запускать
**команды**: `reconstruct <репозиторий>`, `add aspect <…>` / `rebuild aspects`, `validate`,
`apply`, `confirm` / `cancel`. Ответ агента (JSON-массив операций) применяется кнопкой
**Apply as transaction** — он пройдёт через тот же gated-пайплайн правок.

## Проекты и нижняя панель (Ф10 — реализовано)

Рабочая область строится вокруг **проекта**: селектор проектов в верхней панели (переключение
графа, истории чата и состояния вида), кнопка **＋ Project**. Внизу — панель
**Events | Agent | Projects | Validation**:

- **Projects** — список проектов, открытие, создание и **запуск реконструкции**
  репозитория в проект (мастер `⚙ Setup` теперь только настройки, без запуска);
- **Agent** — чат с агентом: команды `design <описание>` (синтез архитектуры, сценарий C),
  `ask <вопрос>` / `rag <вопрос>` (ответ по загруженным документам с цитатами и пометкой
  неподтверждённого), `reconstruct <repo>`, `add aspect <имя>`,
  `проверь модель`, `примени`; долгие команды спрашивают подтверждение («reply «да» to run»).
  `add aspect <имя>` продолжает прогон **от репозитория проекта**, поэтому нужен проект
  с репозиторием (после реконструкции он там уже есть) — иначе чат честно об этом скажет;
- **Validation** — **Check** (формальная валидация + ограничения), **Check with agent**
  (разбор модели агентом: issues и предложенные исправления), **Propose fixes** и
  **Apply fixes** (применение транзакцией с повторной проверкой), история проверок.

![Панель проектов](docs/screens/16-projects.png)

![Панель валидации](docs/screens/18-validation.png)

## Проектирование только по ТЗ

Если у системы **ещё нет кода**, но есть **требования** (ТЗ, заметки), реконструкция работает
в режиме **проектирования**: базовый проход строит архитектуру **по документам** (в ленте —
`no source code: designing the architecture from N document(s)`), сравнение с документацией не
дублируется. Так сценарий «с нуля» можно начать не с пустого холста, а с ТЗ. Режим
отключается флагом `context.design_from_docs`.
